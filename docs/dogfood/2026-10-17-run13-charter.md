### SC-3: re-validation catches reality — the one honest failure

The PRD says *any drift flips the runbook to stale in `lore audit`* within one cycle.
Live drive at HEAD:

1. Injected a deliberate breaking change into `lore/compiler.py:583` (scratch tarball
   only — `--legendary-flag` into the `git rev-parse` check; then a nonexistent-path
   scope into `git log --oneline -5` for check 2).
2. `lore validate --class fast-forward-push-reject --execute` → **"lint drift: check 2
   (error)"**, `drifted_orders=[2]`, history recorded honestly in
   `.lore/validate-history.jsonl`. The DETECTOR works.
3. `lore audit --format json` for the SAME class, SAME SECOND → `status: proposal`,
   no stale column, no lint mention anywhere in the row. The SURFACER does not read
   it.

Root cause (grep chain, no code changed): `apply_lint` exists at
`lore/validate.py:1077`, is flipped on by unit tests, and is called by **nothing in
production** — the only non-test mention anywhere is a docstring at
`lore/__main__.py:531`. Audit's row builder (`_audit_rows()` at
`lore/__main__.py:522-557`) reads `rb.status` straight from the compiler seeds and
never consults the validate history.

Filed as **LORE-064 (P1)**. Fix direction: teach `_cmd_audit` to read
`.lore/validate-history.jsonl` and carry `lint_status` / `lint_ts` columns (local
history, clearly labeled not-attestation), OR add an operator verb that calls
`apply_lint` per class so the flip persists. Also enumerated: LORE-052's
pre-test-body contract (`rb-status` vs `apply_lint` flow) is what the skill teaches;
this run's evidence sharpens why that flow can NEVER fire without a caller.
